## 二、两个重要发现

### 1. C 方案其实不需要做

日志里的 `two_pieces_discount: 95 → 95` 说明：**`copyGoodsCommit` 已经把满2件折扣继承过来了**，草稿里本来就是 95。

也就是说源商品能上架的那些类目设置，复制时已经带过来了 —— 我之前担心的"要手动继承"并不存在。

### 2. 之前的 17000001 是我自己造成的

之前那次提交报 `该类目商品发布必须设置满2件折扣`，但草稿里这个字段明明有值。可能的原因：

- 那次我是**绕过 UI 直接构造 submit 请求**（只带 goods_id + commit_id），平台在校验时读的是另一份状态
- 或者当时草稿还没保存过完整载荷（`action/edit` 从未成功回放过）

现在走完整流程（复制 → 保存载荷 → 提交），就通过了。

### 3. action/edit 报"操作过于频繁"

```
2000000 操作过于频繁, 请稍后再试
```

因为我短时间内对同一个草稿反复抓载荷 + 保存。这是频控，不是错误 —— 而且**它不影响随后的提交**。

对产品的含义：批量操作时必须加**间隔**（每个商品之间 sleep 几秒），否则会被频控。这正是之前设计里提到的「拟人节奏」要解决的问题。

## 五、必须加的两件事（否则批量会失败）

### 1. 频率控制

```
每个商品之间：间隔 5~15 秒（随机）
每个店铺：并发 1，串行
单店每日上限：可配置（建议先 50）
```

`操作过于频繁` 一旦触发，后续都会失败。

### 2. 失败清单 + 断点续跑

批量跑 50 个商品，必然有几个失败。要记录：

```
商品ID | 失败在哪一步 | 错误码 | 重试次数
```

否则跑完不知道哪些没成功。
