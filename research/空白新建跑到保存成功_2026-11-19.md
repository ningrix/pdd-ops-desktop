## 三、纠错：两个之前判断错的地方

### ❌ 错判 1：「自定义尺码在网页端没有入口」

**错的。** 空白新建表单里有两个自定义输入框：

```
placeholder = "自定义鞋码"     ← 鞋类目
placeholder = "自定义尺码"     ← 服装/其他
```

之前说"没有入口"，是因为没滚到规格区（在 y≈3883 的位置，懒渲染）。
**这类商品仍然需要先滚到视口才渲染。**

### ❌ 错判 2：「CDP 的 DOM.setFileInputFiles 能传图」

**在这个页面不行。** 三种方式在同一个干净页面上对比：

| 方式 | 结果 |
|---|---|
| CDP `DOM.setFileInputFiles` | ❌ 调用返回成功，页面计数一直 `(0/10)` |
| 页面内 `DataTransfer` + `new File()` + 派发事件 | ❌ 赋值成功（`el.files.length=6`），计数仍 `(0/10)` |
| **Playwright `locator.setInputFiles(路径)`** | ✅ **`(6/10)`，并真的向 file.pinduoduo.com 发出了 6 个上传请求** |

所以应用现在用 `playwright-core` 做这一个动作。

**踩到的坑**：Playwright 连上后想在 `%TEMP%` 建临时目录，被沙箱拒绝（`EPERM`），
和当年 `%APPDATA%` 写不进去是同一类问题。解法：把 `process.env.TEMP/TMP/TMPDIR` 指到
`app/userdata/tmp`。

## 四、还剩两个技术细节

### 1. 保存后的落库位置未确认

```
保存草稿 → 提示"保存成功!"
commit/list → total = 0
query/commit/detail(206665977810) → 600001 该编辑不存在
```

可能性（都未验证）：
- `type=add` 的草稿走的是另一张表，`commit/list` 只列"编辑中"的
- 保存成功只是"本地暂存"，真正落库要等提交

**下一次要做的**：保存后回到商品列表页，看「草稿」筛选里有没有；或者直接点「提交并上架」看能不能过。

### 2. SKU 预览图需要逐行传，且表格会重渲染

每次上传后 SKU 表格会重新渲染，之前缓存的 locator 全部失效。
必须**每一行都重新定位**，而且要按"某一行是否已有预览图"来判断，不能用 `input.files`
（上传完 React 会把它清空）。

## 五、对「要不要继续做空白新建」的判断

**要。** 现在已经看到：

- 类目自动识别很准（比克隆骨架还省事）
- 不依赖骨架，空店也能发
- 不撞 600102
- 自定义尺码有输入框
- 价格/库存/参考价/满件折扣都能填

剩下的工作量主要在**工程化和稳定性**（不是"能不能"的问题）：
逐行传预览图的健壮性、保存后的落库确认、提交验证。

## 七、当晚复测：上传彻底不通（重要）

6 小时后（23:15）再试，**上传仍然失败**，所以**不是频率限制**。深挖过程与结论如下。

### 7.1 拼多多改版了主图上传

`商品主图` 区域现在有三个按钮，不再是单一的隐藏 file input：

```
[图片空间上传]  [本地上传]  [AI智能做图]
```

对应的 DOM：

```
DIV.goodsCarousel_uploadBtnText__*   文字「上传图片」
DIV.goodsCarousel_originEnter__*     87x87 可点区域
SECTION.goodsCarousel_uploadImgEnter__*
BUTTON  「图片空间上传」/「本地上传」/「AI智能做图」
input[type=file]  只有一个，宽 86，就是「本地上传」的
```

**之前失败的原因之一**：一直在直接给那个隐藏 input 塞文件，而拼多多现在的入口是那三个按钮。

### 7.2 点「本地上传」能读到文件，但上传管线静默中止

```
[说明] Playwright 的 click() 会被遮罩卡住（老坑），必须用 JS 的 el.click()
[结果] JS 点击 → filechooser 事件拿到（multiple = true）→ setFiles(4 张)
       → 页面出现 4 个 blob: 请求（说明文件确实被读进页面了）
       → 但计数始终 (0/10)，没有任何 POST 上传请求，也没有任何报错提示
       → 主图区没有预览，blobImgs = 0
```

**对比**：当天 14:00 左右同样的操作是成功的（计数 `(6/10)`，并抓到真实的
`file.pinduoduo.com/api/galerie/get_endpoint` 请求）。半天之内从成功变成静默失败。

### 7.3 发现一个可疑请求

上传过程中出现：

```
GET http://localhost:16582/zxcv?m=aTBJak03RGJ6S0%40qWlFFWHowZlBIVjdWR3poYUVObnE
```

`m=` 是一段 base64（解码后是乱码前缀 `i0:JkM7DbzK@...`）。这**看起来像本地端口探测**
（反自动化常见手法：扫常见调试端口并上报）。**未确认**，但记在这里，下次优先验证。
