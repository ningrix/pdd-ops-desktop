# 售后助手 · 可行性调查

> 2026-11-22 ｜ 全部结论来自本机真实后台实测（只读，未提交任何操作）
> 结论先行：**能做，而且「打开售后后台」这一层已经验证可用**；真正要做的是分诊 + 文案 + 倒计时，不是自动化提交。

---

## 一、结论

| 能力 | 可行性 | 依据 |
| --- | --- | --- |
| 打开售后工作台 | ✅ 可行，但**不能直接 loadURL** | `/aftersales/aftersale_list` 直接导航会被重定向到 `/aftersales/setup?tab=3`；必须先进 setup 再点「退款/售后」标签 |
| 打开某一张售后单详情 | ✅ **深链已验证** | `https://mms.pinduoduo.com/aftersales-ssr/detail?id=<afterSalesId>&orderSn=<orderSn>` 实测能打开指定单 |
| 读取售后单全字段 | ✅ 可行（DOM 文本） | 见 §三，含倒计时、退货物流、聊天记录 |
| 分诊（该驳回/该同意/该举证/别动） | ✅ 可行，纯本地计算 | 输入是已有的 `afterSales` 数据 + 详情页字段 |
| 文案库 + 举证清单 | ✅ 可行 | 已有 `app/lib/aftersale/appeal.js` 的 7 场景骨架 |
| 一键提交申诉/驳回 | ❌ **不做**（红线） | 见 §六 |
| 自动同意退款 | ❌ **不做** | 平台已有「逾期自动同意退款」，我们不该抢这个动作 |

## 二、后台真实入口（实测）

从后台首页侧栏抓到的全部售后/申诉入口：

| 名称 | 路径 | 实测结果 |
| --- | --- | --- |
| 售后工作台 | `/aftersales/aftersale_list` | 直接导航 → 重定向 `setup?tab=3`；**从 setup 点标签可正常进入** |
| 售后小助手（平台自带） | `/aftersales/aftersale_auto/home` | 能打开，但内容是同一套标签壳，未看到独立自动化配置 |
| 售后设置 | `/aftersales/setup?tab=3` | 退货地址 / 仅退款无需退货 / 售后电话 |
| 工单管理 | `/aftersales/work_order/list` | 有「待处理 / 2小时内将逾期 / 处理中 / 违规已处理」四类 |
| 商家举证 | `/aftersales/merchant_appeal` | **重定向到 `/orders/list`**，不是独立页；举证从订单/售后详情里发起 |
| 极速退款 | `/aftersales/speed_refund` | — |
| 降退款督导 | `/aftersales/supervisor` | — |
| 售后申诉 | `/orders/appeals/aftersale/order` | 见 §四 |
| 异常单申诉 | `/orders/appeals/badOrder` | 见 §四 |
| 拦截快递 | `/orders/interceptExpress` | — |
| 挽单工具 | `/kit/retain-order` | — |

**路由坑（必须记住）**：售后工作台是客户端路由守卫的，`loadURL` 会被打回 setup。正确做法是
`loadURL('.../aftersales/setup?tab=3')` → 等渲染 → 点「退款/售后」标签 → 落到 `aftersale_list`。

## 三、售后工作台与详情页能读到什么

### 3.1 工作台顶部实时数据（阿泽Made 实测）

```text
24小时内将逾期订单数   0 单
24小时内待商家举证     0 单
24小时内平台同意退款   0 单
24小时内将逾期工单数   0 单
```

导航角标（同一时刻）：即将逾期售后 **5**、可申诉订单 **2**、待商家处理售后 **16**、待处理工单 **6**。

### 3.2 快捷筛选（12 个，可直接当分诊维度）

```text
投诉预警 · 待取件即将逾期 · 待处理即将逾期 · 待商家取件 · 待商家处理
待举证即将逾期 · 平台介入待商家处理 · 待商家举证 · 买家催处理
平台处理中 · 待买家处理 · 退货待处理
```

高级查询维度：售后类型 / 售后状态 / 售后原因 / 发货状态 / 操作类型 / 退款金额区间 / 售后申诉 / 申请时间 / 快递拦截 / 极速退款 / 纠纷退款。

表格列：订单信息 / 金额 / 发货状态 / 售后类型 / 售后状态 / 售后协商 / 售后原因 / 操作。

### 3.3 详情页字段全集（实测一条真实单）

实测单：售后编码 `23943351945178`，订单 `261109-285044949393378`，阿泽Made。


**倒计时是可解析的文本**，这是分诊排序的第一键——比我们自己算 48h/36h 更准，因为平台把它算好了。

### 3.4 详情页可用操作（实测存在的按钮）

```text
同意退款
驳回退款（在「其他操作」里，实测是 <span onclick>，非 <a>）
添加留言 / 上传凭证
在线联系消费者
一键申请平台保护（本周剩余申请次数 3 次）
举报恶意售后
添加备注
```

**重要**：「申请平台保护」是平台给的对冲手段——保护期间平台不主动介入，由商家自行协商。这条对我们做分诊很有价值（恶意售后场景直接提示用它）。

## 四、申诉链路实测

### 4.1 售后申诉页 `/orders/appeals/aftersale/order`

6 个 Tab：`可申诉订单 / 申诉记录 / 维权申诉 / 订单赔偿申诉 / 极速退款申诉 / 极速换货申诉`

表格列：订单编号 / 订单信息 / 发货状态 / 实收金额 / 退款金额 / 退款时间 / 申诉项 / **申诉倒计时** / 操作

页面自带的规则提示（原文要点）：

- **申诉失败次数不限制**；但「利用插件、外挂或第三方工具发起批量无效申诉，可能被暂停申诉、驳回申诉」
- **本月申诉复议权益 0/6**（申诉失败订单可发起复议，每月 6 次）
- 有「不展示『暂不申诉』和『低通过率』订单」的筛选开关 —— **平台自己就在做通过率预判**
- 支持「批量暂不申诉 / 批量取消暂不申诉」

这条对我们很关键：平台已经把「低通过率」标出来了，我们的分诊应该**直接复用这个信号**，而不是自己另算一套。

### 4.2 异常单申诉 `/orders/appeals/badOrder`

三种申诉类型（原文）：

```text
异常订单不发货        —— 非正常消费目的或买家原因导致无法发货，通过后无需发货且不计销量
异常订单延后发货      —— 消费者未提供定制信息或要求延后发货
异常订单物流拦截并取消 —— 非正常消费目的导致已发货需拦截，自行拦截成功后平台取消订单并退款
```

表单字段（**这就是之前一直未确认的申诉表单形态**）：

```text
申诉类型（三选一）
申诉原因（下拉）
凭证图片（最多 5 张，单张 ≤ 5M）
申诉描述（文本）
提交申诉 / 取消
```

审核窗口：工作日 10:00–21:00，周期 24 小时。

**所以申诉文案的产出形态是「文本 + 图片清单」，不是纯文本。**

## 六、为什么不做「一键申诉」

三条硬理由，都来自实测：

1. **平台明令反批量**：申诉页原文写着「利用插件、外挂或第三方工具等发起批量无效申诉，可能会被平台采取暂停申诉、驳回申诉等措施」。一键批量 = 直接撞这条。
2. **申诉有次数与复议额度**：失败次数虽不限，但**每月复议权益只有 6 次**，乱申诉会烧掉复议机会。
3. **判责看证据不看文采**：证据链断在自己这边时，文案再好也过不了。自动提交等于替用户把机会用掉。

所以定位是：**助手负责「看清楚 + 写对 + 别漏」，提交永远由人点。**

## 七、建议的产品形态（2~3 天）

### 7.1 售后工作台页（新增 `#pane-aftersale`）

```text
顶部：4 个预警数字（24h 将逾期 / 待举证 / 待商家处理 / 可申诉）
列表：按倒计时升序，每行
  订单号 · 商品缩略图 · 售后类型 · 退款金额 · 状态 · 倒计时 · 建议动作
建议动作枚举：驳回 / 同意 / 举证 / 申请平台保护 / 举报恶意 / 别动（低通过率）
点行 → 隐藏窗口打开详情深链 → 回读字段 → 右侧抽屉显示完整信息 + 文案
```

### 7.2 文案库

```text
app/userdata/appeal-templates.json
{
  id, kind: reject|appeal|evidence|platform_protect,
  scene: 退货退款|仅退款|空包调包|延迟发货|虚假发货|商品质量|物流破损|其他,
  title, body,            // body 支持占位符 {orderSn} {amount} {days} {returnSn}
  evidence: [ ... ],      // 举证清单
  outcomes: { won, lost, lastUsedAt },
  builtin: bool
}
```

命中规则：按 `scene` + 平台「低通过率」信号 → 内置骨架兜底，用户验证过的文案优先，按胜率排序。

### 7.3 分诊规则（纯本地，零远端写）

| 信号 | 建议动作 |
| --- | --- |
| 倒计时 < 24h | 置顶标红「马上逾期」 |
| 退货已签收且 > 24h 未处理 | 「超时即自动退款」高危 |
| 平台标「低通过率」 | 别动（申诉大概率被拒，省复议额度） |
| 申请原因 = 尺码/不喜欢 + 已签收 | 通常同意（驳回难赢） |
| 申请原因 = 质量问题/描述不符 | 举证（要图 + 检测报告） |
| 退货单号为空 / 物流无轨迹 | 先查物流，别急着驳回 |
| 聊天里买家自认（如「拍错了」） | 可驳回，附聊天截图 |
| 同一买家多单售后 | 申请平台保护 / 举报恶意 |

### 7.4 界面红线

- 售后工作台是新页签，不覆盖 `#pane-browser`
- 详情用隐藏窗口读，不劫持用户当前视图（复用 `createHiddenMallWindow`）
- 文案抽屉打开时按 §1.1 摘原生视图
- 所有提交按钮不做，只给「复制文案」和「在后台打开」两个动作

## 九、下一步（建议顺序）

1. **先做详情读取 + 分诊列表**（价值最大，风险最低，不需要碰任何提交）
2. 再补文案库（可先只做「复制文案」）
3. 驳回表单结构确认后，再决定要不要做「半自动填写」（仍不提交）

如果只做一件事：**把 16 个待处理售后按倒计时和「该不该驳回」排好序，点一下能跳到详情页** —— 这就已经解决了「申诉过程繁琐」里最耗时的部分。
