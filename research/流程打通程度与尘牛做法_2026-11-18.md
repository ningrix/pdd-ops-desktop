## 三、尘牛是怎么做的：它有一个我们没有的接口

这是核心区别，一句话讲清：

> **官方 API 有一个专门的「生成规格ID」接口：`pdd.goods.spec.id.get`。
> 我们没有它，只能靠 DOM 让页面自己去生成。**

### 尘牛的完整链路（公开接口，已从 SDK 源码确认）

```
① pdd.goods.cat.rule.get      {cat_id}                    取类目规则
② pdd.goods.spec.get          {cat_id}                    取标准规格组 → parent_spec_id
③ pdd.goods.spec.id.get       {parent_spec_id, spec_name}  ← 生成规格值 spec_id
④ pdd.goods.add               {..., sku_list[].spec_id_list}  一次调用发布
```

**第 ③ 步是关键。** 我们的困境（`spec_id` 是商品私有的、必须由平台生成、
从别的商品抄过来会被静默丢弃）在官方 API 那里**就是一个接口的事**。

### 我们的处境（商家后台内部通道）

```
① 必须克隆骨架       → 撞 600102 时间性频控
② 规格只能 DOM 改    → 页面有输入框才能改（骨架没颜色就改不了）
③ 自定义尺码         → 输入框在，但触发方式不明
④ 或者空白新建       → 传图（已解决）+ 填全表单（未完成）
```

**没有「生成规格ID」这个原子操作**，所以只能借用页面的 UI 让页面自己生成。

### 它真正的护城河不是代码

| 它有的 | 我们没有的 |
|---|---|
| 企业 ISV 资质 | ❌ |
| 应用审核通过 | ❌ |
| 类目权限申请 | ❌ |
| 服务市场入口 | ❌ |
| `spec.id.get` 等完整接口 | ❌ |

**它的代码难度不比我们高，它能调那些接口是因为它有资质。**
这个逆向不出来 —— 你逆向一个 Web SaaS，拿到的还是这套接口的调用方式，
但你没有资质去调。

## 四、所以路径只有两条

### 路 A：拿到资质（配合官方 API）

- 需要：企业营业执照 + 开发者入驻 + 应用审核 + 类目权限
- 门槛：**未确认**具体审核周期和成功率，但服务市场工具的入驻要求是「企业」
- 拿到后的收益：`spec.id.get` 直接解决尺码问题，`goods.add` 一次调用发布，没有任何 DOM 折腾
- 成本：申请成本 + 时间（未知）

### 路 B：把空白新建做完（继续走内部通道）

- 已解决：传图（CDP）、类目自动识别
- 待解决：自定义尺码触发方式、属性填充、价格库存、提交
- 工时：**1~1.5 天**
- 风险：依赖发布页 DOM，平台改版要跟

### 我的建议

**先做路 B**（1~1.5 天能出结果），因为：
1. 路 A 的审核周期不可控
2. 路 B 已经过了最难的一关（图片上传）
3. 做完路 B，即使将来拿到资质，DOM 方案也能作为降级路径

## 六、一句话

> **通了 10 项，不稳 2 项，没通 4 项。** 单店复制→改→提交是通的；
> 跨店遇到自定义尺码就断；空白新建跑到完整表单但没提交成功过。
>
> 尘牛不需要这些折腾，因为官方 API 有 `pdd.goods.spec.id.get` ——
> 它把「生成规格ID」做成一个接口，我们只能借页面 UI 让页面自己生成。
> **它的优势是资质，不是技术。**
