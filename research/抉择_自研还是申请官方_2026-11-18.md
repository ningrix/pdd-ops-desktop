# 抉择：继续自研内部通道，还是申请官方应用

> 2026-11-18 ｜ 基于本项目这几天的实测结论

---

## 一、先纠正一个前提：这不是二选一

很多人会把它想成「两条路选一条」，但实际情况是：

```
路径 A（内部通道 + DOM）
├─ 多店铺管理         ✅ 已通
├─ 登录态持久化       ✅ 已通
├─ 读商品列表         ✅ 已通
├─ 采集箱             ✅ 已通
├─ 商品检测           ✅ 已通
├─ 主图处理/水印      ✅ 已通
├─ 批量队列           ✅ 已通
├─ 改价/改标题/改库存 ✅ 已通
└─ 上架               ⚠️ 通，但受骨架/频控/尺码限制

路径 B（官方 API）
├─ 多店铺管理         ← 同样要用
├─ 登录态             ← 换成 OAuth 授权
├─ 读商品列表         ← 换成 pdd.goods.get
├─ 采集箱             ← 同样要用
├─ 商品检测           ← 同样要用
├─ 主图处理/水印      ← 同样要用
├─ 批量队列           ← 同样要用
├─ 改价/改标题/改库存 ← 换成官方接口
└─ 上架               ← 换成 pdd.goods.add ★
```

**关键事实：路径 A 已经做出来的 8 个模块，在路径 B 里一个都不会浪费。**
路径 B 只替换「上架」那一环（以及顺带把读数据的方式换掉）。

所以真正的决策不是「A 还是 B」，而是：**什么时候启动 B 的资质申请**。

## 二、量化对比

### 2.1 时间成本

| 项 | 路径 A（自研内部通道） | 路径 B（官方应用） |
|---|---|---|
| 资质准备 | 0 | 软著加急 **3~5 工作日**；域名备案 **约 20 天**（可并行） |
| 应用审核 | 0 | **未确认**，按行业惯例 3~15 工作日 |
| 类目权限申请 | 0 | **未确认**粒度，商品发布通常要逐类目 |
| 我写代码 | 空白新建标准码 **3~4h**；跨店差价+详情图 **4~6h**；自定义尺码 **4~8h 且不确定能否成** | API 层 **1~2 天** |
| **你的日历时间** | **约 0 天**（我做） | **约 1 个月**（等证书+审核） |
| **你的实际投入** | 测试、反馈 | 提交材料、等 |

**注意**：路径 B 的 1 个月是**日历时间**，不需要你天天盯着。今天启动，一个月后自然就有。

### 2.2 金钱成本

| 项 | 路径 A | 路径 B |
|---|---|---|
| 软著 | 0 | 常规 **0 元**（30~60 天）；加急 **约 1000~3000 元**（**未确认**，看代理） |
| 域名 | 0 | 约 50~100 元/年 |
| 服务器（备案用） | 0 | 约 100~300 元/年（阿里云轻量最低档够用） |
| 企业主体 | 已有店铺，应该有个体户/公司执照 | 同左 |
| **合计** | **0 元** | **约 200~3400 元**（取决于是否加急软著） |

### 2.3 能力上限对比

| 能力 | 路径 A | 路径 B |
|---|---|---|
| 标准尺码商品上架 | ✅ 能做 | ✅ 能做 |
| **自定义尺码**（`2（90-100）`） | ❌ **网页端无入口，实测确认** | ✅ `pdd.goods.spec.id.get` 直接造 |
| 不受骨架限制 | ✅ 空白新建可以 | ✅ 本来就不需要 |
| 不受 600102 频控 | ✅ 空白新建可以 | ✅ 本来就没有 |
| 逐 SKU 差价 | ⚠️ 能做但要抓载荷改 | ✅ 原生支持 |
| 详情图 | ⚠️ 能做但要抓载荷改 | ✅ 原生支持 |
| 平台改版影响 | ❌ **页面一改就要跟** | ✅ 接口有版本，稳定 |
| 被判定异常操作的风险 | ⚠️ 走后台 DOM，**未确认**判定标准 | ✅ 官方授权，无此问题 |

### 2.4 隐性成本（这块最容易被低估）

| 隐性成本 | 路径 A | 路径 B |
|---|---|---|
| 维护 | 拼多多发布页改版一次就要重新摸一遍 DOM。**这几天我们已经因为 DOM 结构反复调整过 5 次以上** | 接口版本化，极少变 |
| 调试成本 | DOM 问题排查极慢（遮罩、懒渲染、iframe、React 受控组件都会卡住） | 接口报错信息明确 |
| 能力打折 | 自定义尺码这块**永远缺** | 完整 |
| 机会成本 | 你花在这上面的时间，本可以拿去选品/投流 | — |

## 三、我的建议：并行，但**先启动 B 的资质**

### 为什么不是「先做 A 再说」

因为 **B 的等待期是日历时间**：
- 今天启动软著加急 → 3~5 个工作日后就有了
- 不启动 → 永远是 0

**这一个月不管你做不做 A，都会过去。** 而你花 10 分钟提交软著申请，一个月后就多了一条完整通路。

### 为什么不是「只做 B」

因为 B 有 1 个月空窗期。这一个月里：
- 你的鞋类商品（标准码 36~45）用 A 的空白新建**今天就能自动上架**
- 等 B 通了再切换

### 具体时间线

```
今天      你：提交软著加急申请（10 分钟）+ 顺手买个域名开备案
          我：把空白新建「标准尺码商品」链路做完（3~4 小时）
          
第 3~5 天  软著下来
第 20 天   域名备案下来
第 20~35 天 提交应用申请 → 审核（周期未确认）
          
这期间   你已经在用空白新建批量上架鞋类商品了
          
审核通过后 我花 1~2 天写 API 层，把「上架」换成官方接口
          自定义尺码问题彻底消失
```

## 四、如果只能选一个：选 B

### 理由

| 维度 | 判断 |
|---|---|
| **一次性 vs 持续性** | B 是一次性投入（几百~三千元、一个月等待）；A 是**持续投入**（每次平台改版都要返工） |
| **能力完整性** | B 完整；A **永远缺自定义尺码那一块** |
| **风险** | B 是官方授权，无判定风险；A 走后台 DOM，有未确认的判定风险 |
| **已投入是否浪费** | B 不浪费 A 的任何成果（8 个模块全复用） |

**换句话说**：A 是「便宜但一直要养」，B 是「贵一次然后省心」。
你现在这个阶段（要给团队用、要长期跑），**养的成本会超过一次性的成本**。

---

## 五、但有一件事要提醒你

**官方 API 也不会突破 8% 加价限制。** 那是平台对商品发布的比价规则，跟走哪个通道无关。
不要指望「拿到官方接口就能随便加价」——这个期待要提前打掉。

另外「类目权限逐类目申请」这条**未确认具体粒度**，如果羽绒服和登山鞋要分别申请、且审核慢，
那实际可用时间可能比 1 个月更长。

---

## 六、我的最终建议

### 今天（10 分钟，你）

1. **提交软著加急申请**（如果预算紧就选常规，但会拖到 1~2 个月）
2. 顺手买个域名 + 开备案（备案要 20 天，越早越好）

### 今天（3~4 小时，我）

把空白新建的「标准尺码商品」链路补完：
勾码制 → 批量设库存/价格/参考价 → 保存草稿 → 提交

**做完你立刻能用**：鞋类 36~45 的商品，不依赖骨架、不受 600102 限制，直接自动上架。

### 一个月后

软著 + 备案下来，提交应用申请。审核过了我写 API 层。

---

## 七、一句话

> **不要二选一。** 花 10 分钟今天启动资质（它有固定等待期，越早越好），
> 同时我 3~4 小时把标准尺码的空白新建补完，你马上就能用。
>
> 如果真要只能选一个：**选 B**。因为 A 缺的那块（自定义尺码）是补不上的，
> 而 A 的维护成本会一直消耗你。
>
> 但最理性的做法是**两条并行** —— 因为它们的时间线不冲突，成本也不叠加。
