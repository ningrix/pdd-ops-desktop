| 函数 | 作用 |
|---|---|
| `scrollToSpec()` | 把「规格与库存」滚到视口并等渲染。**这个表单是懒渲染的，不滚就根本不存在** |

## 三、剩下的唯一障碍：尺码表

### 现状

```
草稿的 size_spec_id      = 354979932     ← 不是空的
草稿的 size_parent_spec_id = 26908       ← 鞋码
草稿的 SKU 数 = 36
唯一 (规格名, 值) 对 = 13 个 = 4 色 + 9 码   ← 矩阵是对的
```

**尺码表引用存在，但平台仍报「尺码表参数或组别不能为空」。**

### 推断（未确认）

这个 `354979932` 是从骨架（界山XTG）继承来的尺码表。它内部记录的是**骨架原来的尺码值**。
我把尺码改成源的 9 个码之后，**尺码表记录和 SKU 的尺码集合对不上了** → 平台判定"参数为空"。

也就是说：**改了尺码，就必须重建尺码表**，不能沿用骨架的。

### 怎么解（已有完整依据）

尺码表接口已经打通（`research/尺码表接口打通_2026-11.md`）：

```
POST /glide/forward/cabernet/mms/sizespec/action/post
{
  "content": {
    "meta": { "groups":[{"id":1}], "elements":[{"id":N}] },
    "records": [ {"values":{"1":"39","N":"..."}} ]
  },
  "status": 0,
  "class_id": ?
}
```

缺的只有 **鞋类目的 `class_id`**。羽绒服已经试出是 5（class 1~12 全扫定位的），
鞋类目用同样的方法扫一遍即可。

**工作量**：约 1~2 小时（扫 class_id + 生成 content + 绑定 + 验证）。

## 四、顺带修掉的两个错误设计

### ① 骨架跨类目兜底（已删）

之前骨架撞 `600102` 会自动换下一个，包括**换了类目**的。
这次实测证明：鞋类源商品套到羽绒服骨架上，尺码选项是 `150/72A`，根本对不上。

现在硬性要求同品类，没有就明确报错：

```
error : 目标店铺没有同品类商品可作骨架
advice: 目标店需要一个和源商品同类的商品（源类目 11985）。
        跨类目的规格体系完全不同（鞋码 vs 服装码），套不过去。
        办法：先在目标店手动上架一个同类商品当骨架，再回来跑。
```

### ② 尺码勾选靠"猜"（已改）

之前靠 CSS 类名判断 checkbox 是否选中——类名带版本号（`CBX_outerWrapper_5-194-0`），
换个版本就失效，实测把 43 个尺码全点了反而把 SKU 弄成 192 个。

现在改成：**从 SKU 表格读出当前真正生效的尺码**，和目标做差集，只点差异项。
表格是唯一可信事实来源——它列出来的就是真生效的组合。
