## 一、你截图里的错误，根因是我引入的类型漏洞

```
平台操作失败[captureEditBody]: ERR_ABORTED (-3) loading
"载荷 undefined 字节"   →   "载荷解析失败"
```

两件事串在一起：

1. **`ERR_ABORTED (-3)`**：`loadURL` 被同一 webContents 的另一次跳转打断。
   这其实无害——页面往往已经落到编辑页了，但我的代码直接当失败抛出。
2. **真正的坑**：`withPlatform` 在异常时返回 `{ok:false, error, unknown:true}` 这个**对象**。
   `captureEditBody` 把它原样透传给调用方，调用方以为拿到的是载荷字符串：
   - `raw.length` → `undefined`（对象没有 length）
   - `JSON.parse(对象)` → `"[object Object]"` → **「载荷解析失败」**
   
   真实原因（ERR_ABORTED）被吞掉了，你看到的是一句毫无信息量的错。

### 已修三处

| 修法 | 效果 |
|---|---|
| `captureEditBody` 严格返回 `string \| null`，错误存到 `lastCaptureError` | 不会再拿错误对象当载荷 |
| 新增 `gotoUrl()` 容忍 `ERR_ABORTED`：打断后若已在 `goods_add` 页就继续 | 导航抖动不再中断流程 |
| 错误信息透传到 `steps` | 你看到的是「没抓到骨架载荷：ERR_ABORTED…」而不是「解析失败」 |
| 顺手：`main.js` 的 `log()` 改用本地时间 | 修掉日志框里 15:26 / 23:26 跳 8 小时的毛病 |

## 二、更重要的：跨店这条路现在是「必然失败」

`600123 规格信息不合法` 不是我修不好的 bug，是**架构性障碍**：

```
克隆草稿的 SKU 规格树是锁定的
→ action/edit 静默忽略 skus 变更（已验证：返回 ok，重载后规格不变）
→ 强行换 skus 会导致「保存看似成功，提交时规格校验失败」
```

只要源和骨架的规格不同，跨店就必然卡在 `600123`。

### 所以现在跨店能干什么、不能干什么

| 场景 | 结果 |
|---|---|
| 源和骨架**规格完全一致**（同款商品、同类目、同颜色同码） | ✅ 能上，标题图价都能换 |
| 规格不同（绝大多数情况） | ❌ `600123` |

**结论：跨店目前不能用于铺货。** 我不想让你误以为它能用。

## 三、真正的解法（下一步）

**在目标店「从零新建商品」，不是克隆。**

```
现在（错）：克隆目标店自己的商品 → 规格继承骨架 → 锁死
正确（对）：走 goods/add 新建 → 规格空白 → 按源自由填
```

新建路径要自己拼：
- `goods_properties`（类目属性，实测 29 个字段）
- 规格组 + 规格值 → 生成 SKU 矩阵
- 每个 SKU 的价格 / 库存 / 图片
- 尺码表（接口已通）
- 运输模板 / 服务模板

**缺的唯一拼图**：`添加规格类型` 那个入口调的接口。今天点它时被残留弹窗挡住没抓到。
下次刷新页面后第一时间点，应该能拿到。

工作量大概是克隆路径的 3 倍，但这是唯一正确的路。
