# 别人的项目是怎么做「同平台复制上货」的 —— 以及为什么不用逆向尘牛

> 2026-11-18 00:20 ｜ 依据：GitHub 公开仓库 + 官方 SDK 源码

---

## 一、先说结论

**你的直觉方向对了一半，但结论相反。**

- ✅ 你说对了：尘牛的核心能力就是「从零新建商品」，这正是我们卡住的地方
- ❌ 但逆向它拿不到新东西：**它的接口参数是公开的**，我直接从开源 SDK 里拿到了
- ⚠️ 真正的墙不是「不知道怎么写」，是**「没有企业 ISV 资质」**

## 三、决定性发现：官方 `pdd.goods.add` 的规格字段

从 `open-pdd-net-sdk` 的 `AddGoods.cs` 原样摘出来：

```csharp
[JsonPropertyName("sku_list")]
public List<SkuListModel> SkuList { get; set; }

public partial class SkuListModel
{
    [JsonPropertyName("spec_id_list")]
    public string SpecIdList { get; set; }
    // 注释原文：
    // 商品规格列表，根据 pdd.goods.spec.id.get 生成的规格属性id，
    // 例如：颜色规格下商家新增白色和黑色，大小规格下商家新增L和XL，
    // 则由4种spec组合，入参一种组合即可，在skulist中需要有4个spec组合的sku，示例：[20,5]
}
```

**这一行解释了我们所有的失败。**

> `spec_id_list` 里的 id **必须由 `pdd.goods.spec.id.get` 为这个商品生成**。
> 不是从别的商品抄来的，也不是 `parent_id:spec_id` 拼出来的。

所以 `action/edit` 静默忽略我们的 `skus` 变更，完全说得通 —— 我们传的 `spec_id` 是**别的商品的规格值 id**，平台认不出，就直接丢掉。

## 四、完整的官方发品链路（公开的）

```
① pdd.goods.cat.rule.get      {cat_id}                     取类目规则/必填属性
② pdd.goods.spec.get          {cat_id}                     取标准规格组 → parent_spec_id
③ pdd.goods.spec.id.get       {parent_spec_id, spec_name}   ← 生成规格值 spec_id
④ pdd.goods.add               {..., sku_list[].spec_id_list}  发布商品
⑤ pdd.goods.sizespec.meta.get {class_id}                   取尺码表参数定义（含 id）
⑥ pdd.goods.sizespec.template.add                          建尺码表
```

### `pdd.goods.spec.id.get` 的确切参数

```csharp
public partial class GetGoodsSpecId
{
    [JsonPropertyName("parent_spec_id")]
    public long ParentSpecId { get; set; }   // 拼多多标准规格ID，通过 pdd.goods.spec.get 获取

    [JsonPropertyName("spec_name")]
    public string SpecName { get; set; }     // 商家编辑的规格值，如颜色规格下设置白色属性
}
```

### 顺便：尺码表的体重参数 id 也有官方解法

```csharp
public partial class GetGoodsSizespecMeta
{
    [JsonPropertyName("class_id")]
    public int ClassId { get; set; }   // 尺码分类id
}
```

`pdd.goods.sizespec.meta.get {class_id}` 会返回该分类下**全部参数定义（含 id 和名称）**。

**这意味着我之前扫 10000~10049 找「体重(kg)」的做法是白费力气** —— 正确做法是调这个接口，
它会直接告我 `体重(kg)` 的 element id 是多少。

## 五、所以要不要逆向尘牛？

### 不要。理由从「收益低」变成了「根本不需要」

| 你以为能拿到的 | 实际情况 |
|---|---|
| 尘牛怎么调接口 | 走官方开放平台，参数在 SDK 里全公开 |
| 尘牛的私有接口 | 没有。服务市场工具被平台框死，只能用公开接口 |
| 尘牛的编排逻辑 | 「主店发品→子店同步」= 循环调用 ④，没有魔法 |

**逆向一个 Web SaaS，最终拿到的还是这套公开接口 —— 等于绕地球一圈回到原点。**

### 真正的墙：企业 ISV 资质

官方 API 不是有技术就能调：

```
需要：企业开发者账号 + 应用审核 + 类目权限申请
个人/小商家：基本申请不下来
```

**尘牛能做，是因为它有资质。不是因为它的代码比你聪明。**

这也是为什么市面上还有「私域本地接口软件」那一批 —— 它们和我们一样绕开官方 API，
走商家后台的会话通道（就是我们现在的 MMS 内部接口）。**我们这条路其实和它们是同一类，而且已经走通大半。**

## 六、那我们的正解是什么

**不是逆向，是把「生成规格 id」这一步补上。** 两条路：

### 路 A：找内部 MMS 的 spec.id.get 等价接口（首选）

官方有 `pdd.goods.spec.id.get`，商家后台的「添加规格类型」按钮**必然**也调一个内部等价接口
（否则新建商品时也不可能生成规格）。

今天点了两次都点到图片素材弹窗上，没抓到。但这条路**一定存在**，只是要找对元素。

**下次怎么找**（已想清楚，不用再瞎试）：
```
1. 干净重载编辑页
2. 用 document.elementsFromPoint(x, y) 精确定位「添加规格类型」按钮的坐标（不靠 innerText 匹配）
3. 点击后立刻读 window.__mms 的调用记录，或抓 Network
4. 关键词：spec、spec_id、parent_spec_id
```

### 路 B：DOM 自动化补规格（兜底，一定能成）

既然 `action/edit` 不接受外部 spec_id，那就**让页面自己去生成**：

```
① 打开目标草稿编辑页
② DOM 点击「添加规格类型」→ 选「颜色」→ 逐个输入源的色名 → 确定
③ 再点一次 → 选「尺码」→ 逐个输入源的码数 → 确定
④ 页面自动生成 SKU 矩阵，此时每个规格值都有了合法的 spec_id
⑤ 点保存草稿
⑥ 抓保存载荷 → 里面有完整合法的 skus（含 spec_id）
⑦ 只需要把价格/库存/图片按源数据填进去
⑧ 再保存 → 提交
```

**这条路一定能成**，因为它完全是模拟人工操作，平台看不出区别。
代价是比较慢（每个商品 30~60 秒），但比逆向尘牛快得多。

## 七、成本对照

| 方案 | 时间 | 风险 | 可行性 |
|---|---|---|---|
| 逆向尘牛（REA） | 未知，至少数天摸索 + 每次尘牛更新要重逆 | 高 | 拿到的是公开接口，**等于白做** |
| **路 A：找内部 spec 接口** | 半天 | 低 | 高（接口必然存在） |
| **路 B：DOM 补规格** | 1~2 天 | 低 | **确定能成** |
| 买尘牛点券版先用着 | 立刻 | 无 | 但受 8% 加价 + 200 个/店/天限制 |

**建议：路 A 先试半天，不成立刻转路 B。** 两条都不需要 REA。

## 八、REA 真正值得用的地方（不是尘牛）

如果哪天要做下面这些，REA 才有价值：

| 场景 | 为什么 |
|---|---|
| 攻拼多多 `sign` / `anti_content` 加密 | 这是真正的技术门槛，逆向工具能省力 |
| 分析拼多多 App 客户端 | APK 脱壳 / 协议还原 |
| 分析私域本地接口软件 | 看它们怎么绕开官方 API（我们已经自己摸到了） |

**尘牛不在这个清单里。**

## 九、一句话回你

> 你担心成本，这个担心是对的。但省钱的点不在逆向尘牛，
> 而在**别去买它的点券、也别为它花时间逆向** —— 它的技术底牌是公开的，
> 它真正的护城河是**企业资质**，那个逆向不出来。
>
> 我们的路是内部 MMS 通道，已经走通 90%，差的只是「生成规格 id」这一步。
> 这一步我按路 A / 路 B 补上，不需要 REA。
