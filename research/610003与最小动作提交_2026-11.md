# 610003 说明什么，以及提交策略改成「最小动作」

> 2026-11-16

---

## 一、你的日志暴露了真正的问题

```
15:14:42 打开发货编辑页抓取保存载荷 ...
23:14:46 反查 commit 未成功…沿用页面 URL 的 206427818515
```

中间只有 **4 秒**。而抓载荷正常情况下至少需要「页面加载 15 秒 + 点击 + 等请求」。**4 秒结束 = 抓载荷这步直接失败退出了**，日志里也缺了本应出现的：

```
载荷 N 字节
保存: ok
```

也就是说：**我们提交的是一个"没被保存过的" commit**，平台回 `610003 请先保存草稿再提交` —— 这条错误其实是准确的。

而前一次 `600001 该编辑不存在`，是因为 prepare 那条路又把 commit 换了。

---

## 二、根因：prepare（开编辑页→保存）这条流程本身把状态搞坏了

三个错误连起来看：

| 动作 | 结果 |
|---|---|
| 不开编辑页，直接用复制得到的 commit 提交 | ✅ 22:26 实测成功 |
| 开编辑页 + 保存成功 → 用旧 commit 提交 | ❌ 600001 该编辑不存在 |
| 开编辑页但保存没成功 → 提交 | ❌ 610003 请先保存草稿 / 17000001 缺满件折扣 |

**结论：保存草稿会替换 commit，而替换过程中的状态不可控。** 所以我之前那套"先保存再提交"的设计，等于给自己制造了两个新错误。

---

## 三、改成「最小动作优先」

新的提交流程只有四步，默认不做任何多余动作：

```
① 直接用复制得到的 commit 提交
   └ 成功 → 结束（最常见的情况，也是实测唯一验证过的路径）

② 只有报 17000001（缺满件折扣）才去补保存
   └ 保存后改用页面 URL 的 commit 再提交

③ 只有报 600001（该编辑不存在）才读一次页面 commit 重试

④ 都不行 → 给出明确诊断建议
```

这样：

- **正常路径零多余操作** → 不会碰 600001 / 610003
- 只有真的缺满件折扣时才动保存
- 每种失败都有对应的一句话建议

### 失败时会直接告诉你怎么办

| 错误 | 现在会显示 |
|---|---|
| `610003` | 这条草稿在平台上没有内容（保存被打断）。删掉它，重新复制一次再上架。 |
| `17000001` | 满2件折扣没写进去。到编辑页手动设一次（营销 → 满2件折扣 → 95折），保存后再提交。 |
| `600001 / 600009` | 这条草稿已被替换或删除。删掉旧草稿，重新复制一次。 |

## 四、你说的「先把原来的草稿删掉」是对的

平台对同一商品的"新建"有次数/频率限制（`600102 该商品已被新建过`），而且草稿堆多了容易混淆哪个有效。

**建议的操作习惯**（在清理功能做出来之前）：

```
每次测试：
1. 后台 → 商品管理 → 草稿箱 → 把之前的测试草稿全删掉
2. 回到应用，对同一个商品只复制一次
3. 立刻提交上架，中间不要点别的
4. 失败了就删草稿重来，不要在旧草稿上反复试
```

我这边**没有删草稿的接口**（还没抓到），所以暂时只能手动删。这个要补。

## 五、"上架成功但店里看不到"——这是正常的

拼多多提交上架后要过**审核**：

```
提交 → 待审核 → 审核通过 → 在售（才出现在店铺列表）
```

所以 `提交: ok` 只代表"送审成功"，不代表立刻可见。要看状态得去：

- 后台 → **商品管理 → 全部商品**（不是"在售中"筛选）
- 或者状态筛「审核中 / 待发布」

我之前用 `goodsListByGoodsId` + `is_onsale:1` 回读，查的是**已在售**的，所以 total=0 是符合预期的。**这一点我之前没说清楚，是我漏了。**
