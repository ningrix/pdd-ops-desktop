## 一、这轮把错误链彻底理清了

按你的要求我自己跑了完整流程，得到的**错误演进**是这次最有价值的产出：

```
第 1 次提交（草稿库存 = 0）
  → 17000001 该类目商品发布必须设置满2件折扣
     ❗ 这是误导性错误：满件折扣本来就有（UI 里是 9.5 折），
       真正原因是库存为 0，草稿状态不完整

第 2 次：用「批量设置」把库存写成 50 → 保存草稿 → 再提交
  → 17000001 消失
  → 10000014 尺码表参数或组别不能为空
     ❗ 这才是真正的下一个门槛
```

**结论：`17000001 满2件折扣` 在实际场景里往往不是"没设折扣"，而是库存为 0 导致的状态不完整。**

## 二、三个实测事实（纠正我之前的判断）

### 1. 满件折扣的值是 `9.5`，不是 `95`

页面上那个字段：

```
前置文字：「满2件」
输入框 placeholder：5.0~9.9
实际值：9.5
```

所以我之前往载荷里塞 `two_pieces_discount: 95` 是错的写法。**UI 用 9.5 折的写法。**

### 2. 通过 UI 保存草稿，commit 不会变

```
保存前 commit = 206428586943
保存后页面 commit = 206428586943   ← 没变
```

之前那些 `600001 / 610003`，是因为我用**抓来的旧载荷回放 `action/edit`**，载荷里带着过期的 commit，把草稿状态搞乱了。**改用页面自己的「保存草稿」就稳定。**

### 3. 复制不继承尺码表

`copyGoodsCommit` 带走了主图、SKU、价格、运费模板、满件折扣，**但没带走尺码表**。所以从有尺码表的商品复制出来的草稿，尺码表是空的。

## 三、这轮改了什么（都已生效）

| 改动 | 说明 |
|---|---|
| 提交流程改成 DOM 驱动 | 开编辑页 → 等按钮就绪 → 批量设库存 → 点保存草稿 → 读页面 URL 的 commit → 提交。**不再依赖网络抓包**（那步失败率太高） |
| 新增 `setBatchStock` | 用编辑页的「批量设置」写库存（`quantity_delta`） |
| 新增 `hasSaveButton` | 轮询等编辑页真正就绪，最多 30 秒 |
| 新增 `readPageErrors` | 抓页面上的前端校验红字 |
| 提交失败给可执行建议 | 600102 / 600001 / 610003 / 17000001 / 10000014 各自一句话 |

## 四、尺码表模块在哪（已定位）

```
尺码
  └ 可从尺码表模板选择尺码   [全部尺码表]
  └ 自定义尺码排序

尺码表
  └ [停用尺码表]
  └ 尺码参数（表格：尺码 / 操作）
  └ [尺码表信息预览]
```
