# 跨店上架全链路（零上传）——已实测上架成功

> 2026-11-20 凌晨 ｜ 测试号 `阿泽高端made` ｜ 实测结果：草稿转正式商品，在售数 3→4

---

## 一、结论

从采集箱一条别人的商品，到**在目标店真正上架**，全链路跑通：

```
采集箱条目（源：另一个店）
   ↓ 骨架克隆（无上传）
草稿：标题 ✓ 类目 ✓ 图片 14 张（CDN 地址）✓ 4 色 × 16 码 = 64 SKU ✓
   ↓ 改价格 / 库存 / 尺码表字段
   ↓ 提交
在售商品（goods_id 1031888820455，类目 11985）
```

**全程没有上传过一张图。**

## 二、完整配方（按顺序）

### 第 1 步：克隆骨架，得到草稿

`pool:publish` 的前半段即可（切到目标店 → 找同品类骨架 → `create_by_sn` → `copyGoodsCommit`）。
图片来自源商品本身的 CDN 地址，不需要上传。

### 第 2 步：改颜色（每个 SKU 组合都由它派生）

页面：`/goods/goods_add/index?id=<commit>&goods_id=<goods>&type=edit`，滚到「规格与库存」。

颜色行在 `[class*="new-spec-single-color"]` 里，每行一个输入框（排除 placeholder 含「备注」的）。
**骨架颜色数 > 源颜色数时，必须先删多余行**：行内的 `a` 标签文本是「删除」，点它。
删到目标数量后，逐槽位写值（要派发 `input` / `change` / `blur`）。

实测：骨架 5 色 → 源 4 色，删 1 行后填 `春日 / 雅月黄 / 鹭白 / 墨黑`，保存后 SKU 从 80 变 64。

### 第 3 步：勾尺码

`label` 文本为 `欧码`/`英码`/`美码` 的单选先选中；尺码值在 `[class*="package-item-container"]`，
里面是 checkbox。勾完保存，SKU 矩阵自动生成（色数 × 码数）。

### 第 4 步：改价格 / 库存 —— 必须走「抓请求 + 回放」

**为什么不能直接改页面**：多颜色商品的 SKU 表格**只渲染第一个颜色组**（64 行里只渲染 16 行），
另外三个颜色的行根本不在 DOM 里（`document.body.innerText` 搜不到它们的名字），
没有页签、没有下拉、没有分页，「全屏编辑」也只渲染当前组。所以页面填值只会更新第一个颜色。

**做法**：

1. 监听一次「保存草稿」发出的 `POST /glide/mms/goodsCommit/action/edit`，
   拿到 **URL + 完整 headers（含 `anti-content`）+ 原始 body**。
   body 里的 `skus` 数组是**完整的 64 个**，哪怕页面只显示 16 个。
2. 改 `skus` 里每一行：
   ```js
   s.multi_price = 22888;
   s.multi_price_in_yuan = '228.88';   // ← 必改，否则报 2000000 价格参数不一致
   s.price = 25177;
   s.price_in_yuan = '251.77';         // ← 同上
   s.quantity_delta = 50;              // ← 库存写的是增量，不是绝对值
   s.is_onsale = 1;
   ```
   同时把顶层 `market_price` / `market_price_in_yuan` 设成大于最高单买价的值。
3. 把 `size_spec_id` / `size_parent_spec_id` / `is_size_spec_sync_detail` **全部置 0**。
   否则提交报 `10000014 尺码表参数或组别不能为空`。
4. 用页面内的 `fetch` 回放这个请求，headers 用抓到的（去掉 host / content-length 等），
   `credentials: 'include'`，body 用改好的 JSON。

**为什么必须 fetch 回放**：编辑页上 `window.__mms.fetch.sync` 是 **undefined**
（`Object.keys` 里有这个键，但值是 undefined），所以 `ops.js` 的 `applyEditBody` /
`submitDraft` 在编辑页跑不了。必须绕开它，用抓来的真实请求头。

### 第 5 步：提交上架

同一个 fetch 回放方式调：

```
POST /glide/v2/mms/edit/commit/submit
{ "goods_id": <goods>, "goods_commit_id": <commit> }
```

成功返回：`{"success":true,"result":{"is_unpaid_mall_has_no_commit":false,"goods_lock_list":null,"if_mall_wait_audit":false}}`

提交后验证：目标店草稿数 -1，在售数 +1，`listGoods` 里能按标题搜到。

## 三、附带发现：Excel 批量编辑规格（给人用的）

规格区有 `Excel批量编辑规格` 入口，两个接口：

| 用途 | 接口 | 说明 |
|---|---|---|
| 导出 | `POST /glide/mms/goodsCommit/action/downloadExcel` | 请求体要带 `file_name` + **整张表的 content 数组**（缺内容报「表格内容为空」）。返回 `{result:{url}}`，是 `pfs.yangkeduo.com` 的签名地址 |
| 导入 | `POST /glide/mms/goodsCommit/action/uploadExcel` | 上传 xlsx，返回 `{result:{data:[[...]]}}` = 解析后的整张表 |

导出的 payload 里 `content` 就是完整 68 行（说明行 + 2 空行 + 表头 + 64 数据行）。
**但导入只对页面当前渲染的颜色组生效**（实测 4 个颜色都导入成功、确认编辑也点了，
最终只有第一个颜色落到草稿里），所以自动化不要指望它，它适合人工在后台批量改。

## 四、踩到的坑（都验证过）

| 坑 | 现象 | 解法 |
|---|---|---|
| `2000000 价格参数不一致` | 只改了 `multi_price` / `price` | 必须同时改 `multi_price_in_yuan` / `price_in_yuan` |
| `10000014 尺码表参数或组别不能为空` | 提交被拒 | `size_spec_id` / `size_parent_spec_id` / `is_size_spec_sync_detail` 置 0 |
| `600011 店铺处于二级惩罚，不可编辑` | 所有写操作失败 | 目标店被处罚，换店或等解除。同一操作在正常店成功 |
| `__mms.fetch.sync` undefined | 编辑页上调 ops 的业务函数全废 | 抓真实请求头 + 页面 fetch 回放 |
| 提交按钮点不到 | `getBoundingClientRect()` 返回负坐标（固定底栏被挤出视口） | 直接调 `commit/submit` 接口 |
| Excel 弹层残留 | 挡住「提交并上架」 | 先点弹层的「取消」关掉 |
| 页面只渲染 16 行 SKU | 多颜色表格只显示第一组 | 见第 4 步，走请求回放 |

## 五、怎么接进 `pool:publish`

现有 `pool:publish` 的后半段（`setColors` → `setSizes` → `captureEditBody` → `applyEditBody` → `submitDraft`）
应该改成：

1. `setColors` / `setSizes`：保留（DOM 操作在编辑页可用）
2. **把 `captureEditBody` 的结果当基座**（它已经能抓到完整 64 行）
3. 在**主进程**里改 `skus`（价格 / 库存 / `_in_yuan`）+ 尺码表字段置 0
4. 用**编辑页的 fetch 回放**（主进程通过 `executeJavaScript` 发起，headers 由 `captureEditBody` 一并返回）
5. 提交同样走 fetch 回放

不要把 `applyEditBody` / `submitDraft` 用在编辑页上——它们依赖的 `__mms.fetch.sync` 在这一页是空的。
