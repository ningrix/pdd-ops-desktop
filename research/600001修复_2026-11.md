# 600001 的真相：保存草稿会让 commit_id 失效

> 2026-11-16

---

## 一、你日志里的时间线说明了什么

```
14:53:21  导航到编辑页 id=206426154875
14:53:30  点击「保存草稿」 clicked:true
          ……中间空了 31 秒……
22:54:01  提交: 600001 该编辑不存在
```

31 秒 ≈ 抓载荷的超时等待（30 秒）。也就是说：**点保存成功了，但我没抓到载荷**，然后拿**旧的 commit_id** 去提交 → 平台说"这个编辑不存在"。

---

## 二、根因：保存草稿会替换 commit_id

拼多多的草稿每次保存会生成/替换编辑记录。用保存前的 `commit_id` 去提交，就会 `600001`。

这解释了之前看似矛盾的现象：

| 时间 | 情况 | 结果 |
|---|---|---|
| 22:26 | 保存被频控挡掉（`2000000`）→ commit 没变 | 用旧 id 提交 **成功** |
| 22:54 | 保存成功 → commit 被替换 | 用旧 id 提交 **600001** |

**同一个代码，结果相反，区别只在保存有没有真正落库。**

---

## 三、修法：提交前重新解析当前 commit

新增 `resolveCommit(goods)`，用 `create_by_sn` 反查这个商品**当前有效**的 commit id：

```js
call('/glide/v2/mms/edit/commit/create_by_sn', { goods_id })
  → { goods_commit_id: 当前有效 id, old_goods_commit_id }
```

提交流程现在是这样：

```
① 打开草稿编辑页 → 点保存草稿 → 抓载荷 → 补满2件95折 → 回放保存
② 解析当前 commit（create_by_sn）
   如果和原来不同 → 日志会写「commit 已变化：旧 → 新（保存后旧 id 失效）」
③ 用新 commit 提交
④ 若仍报 600001 → 再解析一次、等 2 秒、再提交
⑤ 若报 17000001 → 重存档 + 再解析 + 再提交
```

抓载荷超时也从 30 秒缩到 20 秒，少等一会儿。

---

## 四、你会看到的日志变成这样

正常：

```
提交上架 206426154875（会先做一次完整保存，补满2件9.5折）...
  载荷 6xxxx 字节 / SKU 60
  two_pieces_discount: 95 → 95
  保存: ok
  commit 已变化：206426154875 → 206426201xxx（保存后旧 id 失效）
  提交: ok
已提交上架，去后台「商品管理」看审核状态
```

抓载荷失败但保存生效：

```
  没抓到草稿保存载荷
  反查 commit 失败/成功 → commit 已变化：旧 → 新
  提交: ok
```

即使抓不到载荷，第 ② 步也能把 commit 修正过来 —— 只是这种情况下补不了 95 折，可能会回到 17000001，那时第 ⑤ 步会再补一次。

## 六、这次踩到的三个坑，汇总一下

| # | 坑 | 表现 | 修法 |
|---|---|---|---|
| 1 | 提交前没完整保存 | `17000001 满2件折扣` | 提交前强制抓载荷 + 回放保存，补 95 折 |
| 2 | 保存后 commit 失效 | `600001 该编辑不存在` | 提交前 `create_by_sn` 重新解析 |
| 3 | 操作太密被频控 | `2000000 操作过于频繁` | 保存失败等 8 秒重试 |

这三个都是"提交上架"这条路上的硬约束，现在都内置进流程了。
