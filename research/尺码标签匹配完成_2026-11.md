> 2026-11-16 深夜

## 一、你说的「尺码标都不一样」——这是对的，而且我按它改了

之前我是**按类目关键词**匹配模板，那不成立。你举的例子正好说明问题：

| 商品 | 实际尺码标签 |
|---|---|
| lu鸭绒羽绒服 | `S（80-100斤）` `M（100-120斤）` `L（120-140斤）` `XL（140-160斤）` `2XL（160-180斤）` |
| Lululemon 同款 | `2` `4` `6` `8` `10` |
| 登山鞋 | `39` `40` `41` `42` `43` |

同一个"羽绒服"类目下，尺码标签完全不是一套东西。**所以模板必须按商品的实际尺码标签来选，不能按类目猜。**

---

## 二、已经改成「尺码标签优先」

新的匹配顺序：

```
① 性别过滤（类目名含「女」→ 只允许女装/女鞋模板）
② 尺码标签重合度 ≥ 50% → 直接命中，取重合度最高的模板
③ 标签匹配不上，才退回品牌/款式关键词
④ 再退到类目关键词
```

### 标签归一化（关键）

真实商品的标签带各种后缀，必须先洗：

```
"S（80-100斤）"      → S
"2XL(160-180斤)"     → XXL     ← 2XL 与 XXL 视为同一个
"3XL"                → XXXL
"均码/ONESIZE"       → FREE
"165/90A"            → 165/90A  ← 国标号型保留原样
```

### 数据从哪来

列表接口**不带** SKU 规格，所以尺码标签读不到。改成从**复制后的草稿详情**里取——那条路本来就能拿到完整 SKU：

```
copyGoods 现在会返回 result.sizes = ["S（80-100斤）","M（100-120斤）",...]
```

实测（跨境26小太阳那款）：

```json
{"ok":true, "draftSizes":["S（80-100斤）","M（100-120斤）","L（120-140斤）","XL（140-160斤）","2XL（160-180斤）"],
 "skus":25}
```

### 验证结果（5 个用例全对）

| 类目 | 商品尺码 | 匹配到的模板 |
|---|---|---|
| 女装/羽绒服 | S（80-100斤）…2XL（160-180斤） | **女装上衣** ✅ |
| 羽绒服 | 2, 4, 6, 8, 10 | **Lululemon 短款四格** ✅ |
| 女装/羽绒服 | XS,S,M,L,XL,2XL,3XL | **女装上衣** ✅ |
| 登山鞋/徒步鞋 | 39,40,41,42,43 | **男鞋（欧码）** ✅ |
| 女鞋 | 35,36,37,38 | **女鞋（欧码）** ✅ |

顺便修了一个 bug：尺码匹配最初跑在性别过滤之前，导致**女装被匹到男装模板**。现在性别先过。

## 三、还差什么：写入尺码表的格式

这是唯一剩下的门槛。已经确认的事实：

| 事实 | 依据 |
|---|---|
| **复制不继承尺码表** | 多次复制→提交都报 `10000014 尺码表参数或组别不能为空` |
| 库存 0 会伪装成 `17000001 满件折扣` | 批量设库存 50 后该错误消失 |
| 满件折扣 UI 值是 `9.5` | placeholder `5.0~9.9`，原值 9.5 |
| 尺码表接口存在 | `POST /glide/forward/cabernet/mms/sizespec/action/post`（4000000 = 参数不对，路由通） |
| 我只知道入口位置 | 编辑页有「尺码 / 可从尺码表模板选择尺码 / 全部尺码表 / 尺码参数 / 尺码表信息预览」 |

我尝试从源商品编辑页抓，被 `create_by_sn` 拒绝（`[object Object]`，这条商品今天被复制太多次，状态异常）。
