# 「必须同品类骨架」这个问题有多严重，怎么解

> 2026-11-18 03:20

---

## 一、你说得对，这是当前设计的硬伤

### 会卡住的场景

| 场景 | 结果 |
|---|---|
| 新店第一个商品 | ❌「目标店铺没有同品类商品可作骨架」 |
| 老店上第一个羽绒服（原来只卖鞋） | ❌ 同上 |
| 老店上第一个鞋（原来只卖衣服） | ❌ 同上 |

**每开一个新品类，都要先手动铺一个底。**

### 为什么不能随便拿个骨架凑

克隆骨架会带走它的**类目**（`cat_id`），而类目决定三件事：

```
类目 → 规格类型   （服装是「颜色/尺码」，鞋是「颜色/鞋码」）
     → 尺码体系   （服装 150/72A，鞋 36~45）
     → 必填属性   （29 条 goods_properties，各类目完全不同）
```

实测证据：拿羽绒服骨架去套登山鞋源商品，尺码选项出来是 `150/72A / 155/80A…`，
根本没有 `39/40/41`，硬勾也勾不上。

---

## 二、三条解法，成本和彻底程度不同

### 方案 1：手动铺底（现在就能用，0 开发）

**做法**：每进一个新品类，先在目标店手动上架 1 个该品类商品。之后这个品类就能自动化。

**成本**：
- 每个新品类 10~15 分钟（手动发一个商品）
- 一次性，不是每个商品

**适用**：品类不多（你现在就鞋 + 服装两大类），完全够用。

### 方案 2：改类目（成本低，但未验证）

**思路**：克隆任意商品当「载体」，然后把 `cat_id` / `cat_ids` / `cats` / `goods_properties`
整组换成源商品的类目数据，保存后再改规格。

**为什么可能可行**：这四组是载荷里的普通字段，理论上可替换。

**为什么不一定成**：
- 平台可能校验「类目变更只允许在首次保存前」
- `goods_properties` 里 29 条属性带 `template_pid` / `ref_pid`，换类目后模板可能对不上
- 规格组（parent_spec_id）也是类目绑定的，可能要一起换

**状态**：我今天试了两次，都被 `600102 该商品已被新建过` 挡住（今天对这些商品复制太多次），
**没有拿到结论**。要验证得等限流恢复，或换没动过的商品。

### 方案 3：从零新建（正解，成本最高）

**思路**：走商品发布页的空白新建 —— 选类目 → 填属性 → 加规格 → 提交。
完全不依赖骨架。

**依据**：拼多多官方 API 就是这条路（`pdd.goods.add` + `pdd.goods.spec.id.get`），
开源 SDK `open-pdd-net-sdk` 里有完整字段定义。

**为什么成本高**：
- 要自己拼 29 条 `goods_properties`（每条带 template_pid/ref_pid/pid/vid）
- 要自己生成规格 id（`pdd.goods.spec.id.get`，内部等价接口还没找到）
- 要处理类目必填项校验（满2件折扣、尺码表、服务模板…）

**估算**：3~5 天。而且每一步都可能再冒出新的类目校验。

---

## 三、我的建议：先用手动铺底，别急着做从零新建

### 理由

1. **你的品类就两大类**（鞋、服装）。手动铺底一共 2 次，20 分钟。做从零新建要 3~5 天。
2. **从零新建的坑是未知的**。我们已经踩过：满2件折扣、尺码表、参考价、规格缩略图、commit 失效…
   空白新建会把这些坑重新踩一遍，而且没有骨架给你兜底。
3. **手动铺底还有个隐形好处**：那个手动商品你可以精心做一个「标准骨架」——
   规格齐全、类目属性填对、图片合规。之后所有自动上架都克隆它，质量更稳。

### 具体操作建议

给每个品类在目标店建一个**「母版商品」**：

```
阿泽made
├─ 【母版】鞋-标准骨架     ← 手动发，规格最全（36~45 全码、颜色齐全）
└─ 其它自动上架的鞋        ← 都克隆它
```

母版商品建议：
- 上架后立刻下架（`is_onsale=0`）—— 它只是骨架，不卖
- 但**不能删除**（删了就没骨架了）
- 规格要尽量全，因为自动上架只能从骨架已有的码里勾

这样每个品类只需维护 1 个母版。

---

## 四、什么时候该做「从零新建」

满足下面任意一条再投入：

| 条件 | 说明 |
|---|---|
| 品类超过 10 个 | 手动铺底开始变成负担 |
| 要做成给别人用的产品 | 用户不会接受「先手动发一个」 |
| 母版商品被平台判违规下架 | 骨架没了，全线瘫 |

**现在你自用 + 团队用，2 个品类，方案 1 足够。**

---

## 五、我建议现在就补的一件事

**当骨架缺失时，报错要能指导操作**，而不是一句「没有同品类商品」。

现在是这样：

```
error : 目标店铺没有同品类商品可作骨架
advice: 目标店需要一个和源商品同类的商品（源类目 11985）...
```

已经写了建议，但可以更进一步：**直接告出类目名**，并提示「可以先手动发一个」。
这个改动很小，我现在就能做。

---

## 六、一句话

> 是同品类骨架这个限制确实存在，但它不是「每次上货都报错」，
> 而是「**每个品类第一次上货报错**」——一个品类只需要手动铺一次底。
>
> 你两个品类 = 手动两次，20 分钟。为此去做 3~5 天的从零新建，不划算。
> 等品类多到 10 个以上、或者要给别人用，再投入。
