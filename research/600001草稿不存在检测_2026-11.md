## 一、你这次的 600001 是什么

```
目标: goods=... commit=206437649834
提交(206437649834): 600001 该编辑不存在，或未传goods_id参数
改读页面 commit: 206437649834 → 206437649834   ← 页面也没给出新 commit
重试提交: 600001（同一个错）
```

`改读页面 commit` 前后一样，说明**页面本身也没有这条草稿**。

最可能的原因：**这条草稿在后台被删了**（你清理测试草稿时删掉的），但应用还拿着旧 id 反复提交。

平台对"不存在的草稿"只回 `该编辑不存在，或未传goods_id参数`，措辞含糊，容易被误读成"参数错了"。

## 二、已经加了两道检测

### ① 编辑页自己会报错 → 提前中止

草稿不存在时，编辑页加载出来会显示 `该编辑不存在，或未传goods_id参数`。现在读这个提示，**一发现就直接返回结论**，不再往下点保存。

### ② 提交前做存在性校验

调 `commit/detail` 确认草稿在，再提交。查不到就停。

### 实测（我拿一个故意不存在的 goods + 已删的 commit 测的）

```json
{
  "ok": false,
  "error": "草稿已被删除（编辑页提示「该编辑不存在」）",
  "advice": "这条草稿在后台已经没有内容了。回商品列表重新复制一次再上架。",
  "steps": [
    "目标: goods=999999999999 commit=206437649834",
    "编辑页就绪: 是",
    "页面提示: [... "该编辑不存在，或未传goods_id参数"]"
  ]
}
```

现在是**一次就给出准确结论**，不再重试、不再给"草稿已被替换"这种含糊话。

## 四、操作上的一条硬规则

**复制完就立刻提交，不要隔**。

原因：
- 草稿删了 → `600001`
- 同一商品反复新建 → `600102 该商品已被新建过`
- 隔太久重试 → commit 可能已被替换

正确的节奏是：

```
点复制 → 勾「直接提交上架」→ 等结果
失败 → 不要在旧草稿上重试，回列表重新复制
```
