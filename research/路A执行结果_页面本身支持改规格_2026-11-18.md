# 路 A 执行结果：不用找接口了 —— 页面本身就支持改规格

> 2026-11-18 00:40 ｜ 实测记录

## 一、结论（这条推翻了原先的判断）

**不需要找 `pdd.goods.spec.id.get` 的内部等价接口。**

编辑页的规格区**本来就是可编辑的表单**：
- 颜色是**自由文本输入框**，可以随便加、随便删
- 尺码是**标准模板 + 复选框**，可以勾选
- 保存时**页面自己会生成合法的 `spec_id`**

之前我们一直用 `action/edit` 回放载荷去改 `skus`，绕过了页面这一层，
所以平台拿到的 `spec_id` 是别的商品的，直接静默丢弃。

## 三、尺码区的真实结构（比预想复杂）

尺码不是自由输入，是**标准码体系 + 复选框**：

```
通用 / 中国码 / 欧码 / 英码 / 德码 / 美码 / 均码        ← 7 种尺码体系
[全选以下规格值]

中国码模式下的标准码值（全部预置在页面上）：
  150/72A  150/76A  155/80A  160/84A  165/88A
  170/92A  170/96A  175/100A 175/104A 180/108A 180/112A …
```

**含义**：尺码不能任意填，只能从平台标准码表里勾。
每个类目的标准码表不同（服装是国标号型，鞋是 36~46）。

我试点了「通用」，结果**该草稿的尺码值被清空，SKU 从 33 行降到 20 行**。
说明「通用」不是自由输入，而是另一套码表。

### 对我们的影响

| 源商品尺码类型 | 能否搬 |
|---|---|
| 标准码（39/40/41… 或 S/M/L） | ✅ 在模板里勾选即可 |
| 自定义标签（`S（80-100斤）`、`2（90-100）`） | ⚠️ 需要确认对应类目的标准码表里有没有；没有的话只能用「商品规格」的自定义方式 |

**注意**：`lu鸭绒` 那款源的尺码是 `S（80-100斤）` 这种带注释的自定义写法，
但它**自己的商品**能上架，说明平台允许这种写法，只是入口可能不同。

## 四、所以路 A 的正确落点是什么

不是找接口，是**把 DOM 操作做对**。完整方案：

```
① 目标店克隆骨架 → 草稿
② 打开编辑页
③ 颜色：清空现有输入 → 逐个填入源颜色（已验证可行）
④ 尺码：按源尺码匹配标准码表 → 勾选对应复选框
   （匹配不上时：保留骨架尺码并明确告警，不硬塞）
⑤ 保存草稿（页面自己生成全部 spec_id）
⑥ 读页面 URL 的 commit
⑦ 提交
```

**关键差别**：第 ⑤ 步必须由**页面自己**执行（点「保存草稿」按钮），
不能我们回放 `action/edit`。这是整件事的核心。

## 五、已写好的基础设施

这轮为了抓包，给应用加了两个调试接口（`main.js` + `preload.js`）：

```js
window.pdd.netStart()   // 主进程 webContents.debugger 开始记录全部请求
window.pdd.netStop()    // 停止并返回 {count, records:[{url,query,method,body}]}
```

**为什么需要**：外部 CDP 在 `WebContentsView` 上抓不到 Network 事件（只能收到 1 条），
主进程的 debugger 才可靠 —— 和 `captureEditBody` 用的是同一个机制。

这两个接口是通用的调试能力，以后找任何接口都能用。
