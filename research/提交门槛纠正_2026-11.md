# 纠正：尺码表不是提交门槛；真门槛是类目必填项

> 2026-11-16

---

## 一、先认错

我之前说「提交上架被尺码表拦住」——**这个判断错了**。

你的实际情况是：每个商品都有尺码，有的有尺码表有的没有，**都能提交**。这说明尺码表不是通用硬门槛。

我那个 `10000014 尺码表参数或组别不能为空` 的来源是一个**我用脚本反复提交过的测试草稿**（登山鞋 206366952022），它的状态被折腾坏了，不能代表真实商品。

---

## 二、重新验证：真门槛是「类目必填项」

修掉 `goods_id` 那个 bug 之后，用真实商品（山行2代 GTX 登山鞋）跑完整链路：

```
① 读取商品      ✅  1 个在售（60 SKU，库存 1312）
② 复制成草稿    ✅  commit=206422298414 / goods_id=1030495631360（20 图 / 60 SKU）
③ 提交上架      ❌  17000001 该类目商品发布必须设置满2件折扣
```

**这个错误比之前有价值得多**：它说明提交已经过了参数校验，卡在**类目特有的上架必填项**上。

### 已找到对应字段

之前抓的 `action/edit` 载荷里就有：

```
two_pieces_discount = 95      ← 满2件折扣的折扣率
```

同族字段还有 `max_two_pieces_discount` / `min_two_pieces_discount` / `recommend_two_pieces_discount` / `two_pieces_rule_vo`。

也就是说：**这个类目要你在发布前开启「满2件折扣」，值是 95（95折）这样的折扣率。** 你手动提交能成功，是因为后台 UI 里帮你带上或让你设过了。

---

## 三、这类"类目必填项"的规律

拼多多按类目有不同的发布前置条件，同类问题会反复出现：

| 错误码 | 含义 | 需要的字段 |
|---|---|---|
| `17000001` | 该类目必须设置满2件折扣 | `two_pieces_discount` |
| `10000014` | 某些类目要求尺码表 | `size_spec_*`（schema 待抓）|
| 其他 | 可能有：售后模板、发货时效、资质、服务承诺… | 各自字段 |

所以「一键上架」真正的挑战不是接口，而是**收集每个类目的必填项并自动补齐**。

---

## 四、可行的解法（按工作量排）

### 方案 A：类目必填项模板（推荐）

和尺码表模板同一个思路：

```json
{
  "cat_keywords": ["登山鞋", "徒步鞋", "户外鞋靴"],
  "presets": {
    "two_pieces_discount": 95
  }
}
```

复制后、提交前，把 `presets` 合并进 `action/edit` 载荷回放一次，再提交。

**优点**：一次配置，长期复用；报错会告诉我们缺哪个字段，逐个补进模板即可。
**缺点**：需要按类目积累，遇到新类目要补一次。

### 方案 B：报错驱动的自动补全

```
提交 → 拿到 error_code → 查「错误码 → 补全动作」表 → 补字段 → 重提
```

好处是不用穷举类目；坏处是第一次遇到新类目必然失败一次。

### 方案 C：从源商品复制

源商品能上架，说明它已经满足了类目要求。理论上把这些字段（`two_pieces_discount` 等）一起克隆过来就行——但 `copyGoodsCommit` 没带上，需要复制后手动 `action/edit` 补。

**这是最优解**：不依赖类目表，直接从源商品继承"已满足的发布条件"。

---

## 五、建议的下一步

我倾向 **C + A 组合**：

1. 复制后，把源商品详情里的这些字段（`two_pieces_discount` 等）写进草稿 —— 因为源商品本来就能上架
2. 补不到的（比如尺码表这种没继承的），用类目模板兜底
3. 提交；若仍报错，按 error_code 累积到模板里

这样第一次就能通过大部分类目，剩下的靠报错迭代补齐。

**需要你确认一件事**：你手动提交成功的那几个商品，是不是在后台手动设过「满2件折扣」？如果是，我就按 C 方案做继承；如果后台没设也能提交，说明这个字段有默认值，我需要再抓一次你提交时的载荷。
